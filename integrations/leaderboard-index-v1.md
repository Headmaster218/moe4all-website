# 排行榜精简总库字段清单

日期：2026-10-21。本文描述全量静态索引。字段定义及校验以 `community/leaderboard-model.mjs` 为准；生产生成器位于 MoE4All 主仓的 `scripts/build-benchmark-index.mjs`，本仓 `scripts/build-leaderboard.mjs` 仅用于本地预览。网页读取器为 `community/leaderboard-loader.mjs`。数据链路与发布边界见 [排行榜数据方案](leaderboard-data-plan.md)。

## 目标与组织

首次下载一份压缩后的全量核心索引，之后在客户端完成模型、显卡、内存、上下文及其他条件的筛选、排序和分页。只收录经审核并合入 Git 的 Benchmark；`.m4e` 和待审数据不进入性能总库。

总库保存展示、比较和判定测试条件是否可比所需的摘要，不保存完整报告。字段分为：

1. **全局目录**：版本、下载与 Git 来源信息，只保存一次。
2. **报告摘要**：模型、硬件、配置与测试协议，每份报告保存一次。
3. **上下文摘要**：实际测试深度及 Prefill，每个报告的上下文保存一次。
4. **测量摘要**：每个 Decode 并发条件的汇总，另保留手动测量和失败摘要。

这些是逻辑层级，不要求建立 SQL 表或每层单独下载。传输时采用列式 JSON、字典引用、常量列以及 Brotli / gzip；报告、上下文之间用包内短引用关联。

例如一份报告有 3 个上下文、每个上下文测 x1 / x2 / x3，则保存 1 份报告摘要、3 份上下文摘要（其中最多 3 份 Prefill）和 9 条 Decode 摘要。不能把同一份 Prefill 复制成 9 次独立实测。

## 全局目录

| 内容 | 保存规则 |
| --- | --- |
| 格式与数据版本 | schema / 编码版本、数据内容版本、生成时间 |
| 数据规模 | 报告数、上下文数、各类测量数量 |
| 压缩包 | Brotli / gzip 的资源地址、压缩字节数、明确校验对象的 SHA-256；客户端只下载一种 |
| 解码边界 | 声明未压缩大小和行数，读取器还须使用独立硬上限，不能盲信声明 |
| Git 来源 | 数据仓库、包含全部原件的完整 commit、路径格式版本 |

模型列表、GPU 列表、各筛选范围可在核心索引加载后本地推导，不必为了目录再复制一遍所有枚举值。若需要加载前展示，可加入小型摘要，但不能与主数据各自人工维护。

## 每份报告的摘要

“基础”表示这是索引固定支持的内容，不表示每份历史报告都已采集到。未提供的单个值仍为 null。“可选扩展”只能提取明确存在且来源可验证的字段，不是要求网页或 CI 猜出数据。

| 分类 | 基础内容 | 可选扩展与限制 |
| --- | --- | --- |
| 身份 | 报告 ID、原始 UTC 生成时间、引擎版本 | 引擎 build commit 若原件明确提供则保留；它与全局数据仓库 commit 不是一回事 |
| 测试来源 | 原件 schema、quick / standard / full / manual、手动测试种类 | 用于详情与可比性判断，不强制增加这些 UI 筛选项；通过校验不等于维护者独立复测 |
| 模型 | 完整模型名、模型架构、模型总字节数 | 量化名称、等效 bpw 仅在原件有明确字段时保存；不从文件名猜出精确 bpw |
| 系统 | OS、系统架构（如 x86_64 / aarch64）、明确记录的 Backend | 没有 Backend 字段时不把 GPU 类型或型号当作 Backend |
| GPU | 型号、VRAM 总字节数 | 集成 GPU、统一内存标记有明确记录时保留，避免把统一内存设备的 RAM 与 VRAM 错当成两份独立容量 |
| CPU | 型号、逻辑线程总数 | 配置线程数另外保存，不与硬件逻辑线程数混用 |
| RAM | 物理总字节数、内存代际 | 条数、配置速率的简要分布；混插时保留分布，不捏造一个统一频率；不带完整模块对象或厂商料号 |
| PCIe | 当前 / 最大代际、当前 / 最大宽度 | 当前 / 最大理论单向 GB/s、检测来源；无 PCIe 或未采集保持 null，不把理论带宽当实测 H2D |
| 模型盘 | 磁盘型号、介质类型、总线类型 | 不存盘符、路径、序列号和分区标识；有盘类型时不把 HDD 或未知设备一律称为 SSD |
| 盘读测 | 测试模式、顺序读 MiB/s、random 64K MiB/s、random 64K IOPS、缓存分类、物理读取占比 | 均按原报告读测定义；应用可见读速不等于 SSD 物理吞吐；未采集不填 0 |
| 配置策略 | 自动激进 / 自动保守 / 手动 / 未知 | 只有原件明确支持相应语义时才归类；`profile=manual` 是手动测试，不等于配置策略一定是全手动 |
| KV 与 MTP | K / V 类型、MTP 开关 | 未报告为 null；不把未知显示成 OFF，不为缺失的接受率或预测深度编造默认值 |
| 执行配置 | 配置 ubatch、配置 CPU 线程、配置 RAM / VRAM 预算、额外 VRAM reserve | 实际 ubatch / 实际预算只有单独记录时才保存为实际值；配置值与实际值分开，自动或比例预算不擅自解析成已落实的字节数 |
| 分页与提交 | Host DMA 开关、submit dispatch cap，若原件明确记录 | 不从日志或性能高低推断隐藏开关；其余完整分页设置留在原件，除非后续确实用于解释榜单差异 |

重复的型号、配置枚举等可以跨报告字典去重，但一份报告的身份不能因为硬件相同就合并掉。没有机器名或序列号时，不尝试断定两份报告来自同一台物理电脑。

## 每个上下文的摘要

| 内容 | 保存规则 |
| --- | --- |
| 关联报告 | 包内报告引用 |
| 请求上下文 | `requested_context_tokens`，与实际长度分开 |
| 实际测试深度 | 实际 prompt、Decode 计分开始 / 结束长度；多路不同可保存明确命名的 min / max 摘要，逐路原值留在原件 |
| 上下文类型 | 真实 / synthetic / 无预置深度 / 未知，只按原件明确标记归类 |
| Prefill | 原件的 tok/s、实际 prompt tokens、evaluated tokens、测量秒数；必要时保留 setup slots 作为条件 |
| 失败情况 | Prefill 等阶段是否失败、失败阶段及数量；详细错误正文留在原件 |

实际深度范围是主动定义的摘要，不冒充原始逐路数组的无损副本；无损压缩仅指编码器完整还原这份已定义的精简索引。

不能因为 `evaluated_tokens` 较少或速度很高就推断“冷请求”或“全部 cache hit”。如需缓存条件，须来自原件明确字段；未报告就标为未知。

## 每个测量条件的摘要

### 自动 Decode

| 内容 | 保存规则 |
| --- | --- |
| 身份 | 上下文引用＋并发数；可构造稳定的报告 ID / 上下文 / 并发标识 |
| 速度 | 原件的总平均 Decode，以及前 / 中 / 后段均值，单位 tok/s |
| 指标含义 | 自动套件的并发总吞吐量，不冒充每路速度；不再简单除以并发数生成一个“实测单路速度” |
| 轮次 | 实际完成轮数与请求轮数分开；部分失败不能显示成全部完成 |
| 计分协议 | 每路预热 tokens、计分 tokens 等必要协议参数，在报告级保存一次即可 |
| 状态 | 成功 / 部分失败 / 失败，以及能关联到该条件的失败阶段与数量 |

使用原件已经定义的 `overall_tokens_per_second` 与 `section_mean_tokens_per_second`，不在 CI 中擅自换成另一个平均公式。失败条件的速度为 null，不是 0；未知条件的字段也不使用默认值伪装成已知。

### 手动测量

保留手动结果类型（Prefill / Decode）、原始平均速度、明确记录的轮次、prompt / generation tokens 和 depth mode 等可比性信息。未报告并发和分段速度时保留未知，不伪造 x1 或前中后段。仅有手动 Prefill 的报告也必须能出现在 Prefill 榜，而不是因为没有 Decode 数组而丢失。

手动测量不直接混成自动套件的同一协议。测试来源是技术元信息，不改变“配置策略”这一个独立维度。

### 失败摘要

只有失败、没有成功速度的上下文或并发条件仍保留轻量状态，以免把失败样本静默丢掉。失败阶段、并发和轮次若原件能明确关联则保留；不能明确关联时只算到报告或上下文层，不重复计入每一个并发条件。失败类别只有稳定来源时才保留，不从任意错误文案猜分类。

## 不进入全量核心索引

- 原始 `.m4b` / `.m4e` 正文、完整 decoded JSON、可读 header 摘要。
- 启动日志、trace、每轮每路时间序列、完整错误正文和堆栈。
- 估算器内部过程、全部 GGUF metadata、张量表、完整 SMBIOS 和磁盘枚举。
- 机器名、用户名、序列号、本地路径、完整命令行、凭证、会话 / 回执 token。
- 为每个筛选组合预计算的结果文件、每条记录重复的 Git 长链接和逐报告 commit/path。

已归档原件仍通过全局数据仓库 commit＋报告 UTC 月份＋ID 构造链接。索引发布所需的文件 hash 校验并未取消，只是不逐条传给排行榜页面。

## 当前报告格式的事实与缺口

本轮只读核对了引擎维护工作区的 `crates/infr-cli/src/main.rs`、`scripts/infr-wizard.ps1`、`crates/infr-core/src/config/mod.rs`，以及网站现有 `community/submission-codec.mjs`。

| 内容 | 当前核对情况 |
| --- | --- |
| 身份、CPU / GPU / RAM、上下文、Prefill、Decode 均值与分段 | 自动套件已有相应字段；个别字段可为 null |
| PCIe、RAM 代际 / 模块、模型盘读测 | Windows 向导会尝试补充，其他平台或探测失败时不能保证存在 |
| 量化与等效 bpw | 自动报告示例构造未统一写出明确量化字段，不能因为文件名有量化文本就宣称已采集精确 bpw |
| Backend、实际 ubatch / 实际预算 | 当前自动报告主要记录 `configured_*`，不能承诺已有完整运行时实际值 |
| 配置策略 | 自动套件写出的 `AutoProfile` 有 Conservative / Aggressive；显式配置可覆盖部分参数。不能仅凭存在显式 ubatch 就推断整套是“全手动” |
| 当前静态投影 | 已对齐 `configured_*` 与旧 `ubatch` 兼容字段，配置与实际值分列；支持手动测量、Prefill-only、失败条件与未知并发 |

没有修改引擎或伪造缺失字段。缺失采集能力继续显示为未知，不因网页已经支持字段就宣称每份报告均已采集。投影、压缩还原、来源路径及浏览器读取边界有独立测试。

## 传输字段与编码

`moe4all-leaderboard/1` 固定三张逻辑表的字段顺序，不将任意用户字段名带进浏览器对象。`FIELDS` 是唯一编码次序；读取器不接受缺列、额外列或无效引用。

- `reports`：身份、模型、系统与硬件、PCIe、模型盘读测、配置、预热与计分协议、手动 prompt/depth、失败摘要及本地 demo 标记。
- `contexts`：`report` 短引用、请求上下文、实际 prompt/start/end 的 min/max、Prefill 速度与 token/秒数/setup slots、失败摘要。
- `measurements`：`context` 短引用、`kind`、并发、总平均与前中后段速度、完成轮数、状态与失败摘要。

每张表写 `{n,c}`：`n` 为行数，`c` 为按固定字段排列的列。常量列为 `{k:值}`；普通列为 `{v:[值]}`；字典列为 `{d:[去重值],v:[字典下标]}`。编码器选择较短表示，不截断数字。空表严格为 `{n:0,c:[]}`。

manifest 记录 schema、内容 SHA-256 版本、生成时间、来源、三表行数、解码字节数以及 Brotli/gzip 各自的 URL、字节数与 SHA-256。压缩资源扩展名为 `.br.bin` / `.gz.bin`，由读取器显式解压，避免服务器 Content-Encoding 与客户端重复解压。详细硬上限与缓存规则见数据方案。
